## 1. Research Question & Scope

### 1.1 Core Hypothesis
> *"For previously unseen PostgreSQL query patterns, does using benchmarked historical execution outcomes to rank deterministic, safety-validated candidate recommendations improve measured outcomes over a planner-only baseline, without increasing unsafe or regressive recommendations?"*

### 1.2 Policies Under Evaluation

All three policies operate on the **identical, deterministic candidate pool** generated by Phase 1 and validated by HypoPG and SafetyAssessor. No policy can invent new candidates, alter index structures, or bypass approval gates.

```
                  ┌──────────────────────────────────────────────┐
                  │          Unseen Test SQL Query               │
                  └──────────────────────┬───────────────────────┘

                  └──────────────────────┬───────────────────────┘

                  ┌──────────────────────────────────────────────┐
```

1. **Policy A — Planner-Only Baseline ($S_{\text{Planner}}$):**
   - Selects the Phase 1 default baseline candidate ($c_{\text{baseline}}$) based strictly on heuristic plan node properties and HypoPG simulated cost reduction.
   - Zero retrieval, zero historical case memory.
2. **Policy B — Similarity-Based Retrieval ($S_{\text{Sim}}$):**
   - Evaluates similarity support from historical cases in the **frozen TRAIN** partition using token-hash cosine similarity.
   - $$S_{\text{Sim}}(c) = \Delta_{\text{HypoPG}}(c) + \alpha \sum_{h \in \text{TRAIN}, \text{key}(h)=\text{key}(c)} \text{Sim}(q, q_h)$$
   - Uses zero historical runtime outcome values (does not observe success or regression magnitude).
3. **Policy C — Outcome-Aware Retrieval ($S_{\text{Outcome}}$):**
   - Incorporates verified measured benchmark outcomes from eligible **frozen TRAIN** cases (`provenance == MEASURED`, `is_verified == True`, `verification_state == VERIFIED_MEASURED`).
   - $$S_{\text{Outcome}}(c) = \Delta_{\text{HypoPG}}(c) + \beta \sum_{h \in \text{TRAIN}_{\text{meas}}, \text{key}(h)=\text{key}(c)} \text{Sim}(q, q_h) \cdot \Phi(\Delta_{\text{meas}}(h))$$
   - Where $\Phi(\Delta) = \Delta$ if $\Delta \ge 0$, and $\Phi(\Delta) = \Delta \cdot \lambda_{\text{reg}}$ if $\Delta < 0$ ($\lambda_{\text{reg}} \ge 1.0$ penalizes historical regressions asymmetrically).
   - If no verified historical evidence matches candidate keys, deterministically falls back to Policy A.

## 2. Corpus Design & Target Sizing

### 2.1 Measured Corpus Targets
To support a defensible experimental comparison between Policies A, B, and C without overclaiming statistical power:

| Target Tier | Measured Cases ($M$) | Canonical Templates ($T$) | Cases / Template | Purpose & Qualification |
| :--- | :--- | :--- | :--- | :--- |
| **Minimum Defensible Target** | **12 cases** | **6 templates** | **2** | **Minimum defensible target**: Allows a non-trivial grouped train/test partition (e.g. 4 Train templates / 8 cases, 2 Test templates / 4 cases) with zero template overlap. |
| **Desired Target** | **20 cases** | **8 templates** | **2–3** | **Desired target**: Provides 5–6 Train templates (14–15 cases) and 2–3 Test templates (5–6 cases) across multiple tables, selectivity tiers, and query shapes. |

### 2.2 Critical Methodological Clarifications on Corpus Size
1. **No Guarantee of Statistical Significance:** Neither 12 cases nor 20 cases guarantees statistical significance. These targets define the minimum scale required to test the algorithmic mechanics of grouped template partitioning, frozen historical retrieval, and outcome-aware candidate ranking on live PostgreSQL.
2. **Empirical Case Qualification:** The final corpus size is not predetermined arbitrarily; it will be strictly determined by the number of valid, non-noisy measured cases actually obtained and verified during Phase 6A execution.

- **DML / Write queries:** `INSERT`, `UPDATE`, `DELETE` (AutoDBA diagnostic scope is strictly read-only EXPLAIN analysis).

## 3. Leakage-Controlled Train/Test Partition Strategy

### 3.1 Strict Grouped Template Splitting (`split_strategy.py`)
To ensure that test queries represent genuinely **unseen query patterns**:
1. Every query is canonicalized via `canonicalize_sql(query)` (normalizing literals to `?`, standardizing identifiers).
2. The canonical string is hashed: $\text{template\_hash} = \text{SHA256}(\text{canonical\_sql})$.
3. All cases sharing the identical $\text{template\_hash}$ are assigned as a single indivisible block to **either TRAIN or TEST**.
4. Test split ratio: $30\%$ (e.g., 6 Train templates / 2 Test templates).

```
   ALL MEASURED CASES (M=20)
               │
               ▼
   Group by template_hash
   ├── Group T1 (customer_id = ?)            ───► TRAIN
   ├── Group T2 (total_amount > ?)           ───► TRAIN
   ├── Group T3 (customer_id + amount)       ───► TRAIN
   ├── Group T4 (status = ?)                 ───► TRAIN
   ├── Group T5 (quantity > ?)               ───► TRAIN
   ├── Group T6 (unit_price > ?)             ───► TRAIN
   ├── Group T7 (quantity + unit_price)      ───► TEST  (Unseen pattern)
   └── Group T8 (customer_id + status)       ───► TEST  (Unseen pattern)
```

### 3.2 Formal Leakage Invariants
- **Invariant 1 (Zero Template Leakage):** $\text{Templates}(\text{TRAIN}) \cap \text{Templates}(\text{TEST}) = \emptyset$.
- **Invariant 2 (Zero Instance Leakage):** $\text{CaseIDs}(\text{TRAIN}) \cap \text{CaseIDs}(\text{TEST}) = \emptyset$.
- **Invariant 3 (Retrieval Boundary):** Policies B and C can retrieve historical cases strictly from $\text{TRAIN}$. The TEST set is never indexed in the retriever.
- **Invariant 4 (Complete Partition):** $|\text{TRAIN}| + |\text{TEST}| = M_{\text{total}}$.

### 3.3 Placement of Existing Pilot Case (Memory ID 1)
Memory ID 1 (`SELECT * FROM orders WHERE customer_id = 42;`) belongs to template `T1`. In the experiment partition, `T1` will reside in the **TRAIN** partition, serving as an authoritative verified historical measurement.

## 4. Candidate Availability, Decision Boundaries & Oracle Definition

### 4.1 Single-Candidate ($|C|=1$) vs. Multi-Candidate ($|C| \ge 2$) Queries

| Candidate Set | Selection Dynamics | Role in Evaluation |
| :--- | :--- | :--- |
| **Single Candidate ($|C|=1$)** | All three policies select the exact same baseline candidate $c_{\text{baseline}}$. | Validates pipeline stability, execution consistency, and measurement repeatability across policies. |
| **Multi-Candidate ($|C| \ge 2$)** | Policies can actively diverge based on planner heuristic vs similarity vs historical outcome support. | **Core Discriminative Test**: Demonstrates whether outcome awareness avoids regressions or selects superior index configurations. |

### 4.2 Exact Candidate Key Matching Rule
A historical case $h$ can only contribute support to a candidate $c$ if their canonical index keys match exactly:
$$\text{key}(h) = (\text{table}, \text{index\_method}, (\text{col}_1, \ldots, \text{col}_k)) = \text{key}(c)$$
- Column order matters: B-tree `(customer_id, order_date)` $\neq$ `(order_date, customer_id)`.
- Index method matters: `btree` $\neq$ `hash` $\neq$ `gin`.

### 4.3 Oracle Definition & Evaluation Protocol

To rigorously benchmark selection quality without conflating heuristic ranking with true execution performance, we establish the following formal distinctions:

1. **Policy-Selected Candidate ($c_\pi(q)$):** The specific candidate selected by policy $\pi \in \{A, B, C\}$ from the eligible candidate pool $C_{\text{eligible}}(q)$.
2. **Candidate-Level Measured Outcome ($\Delta T_{\text{meas}}(c, q)$):** The actual empirical runtime improvement percentage measured on PostgreSQL when candidate index $c$ is physically created and benchmarked for query $q$:
   $$\Delta T_{\text{meas}}(c, q) = \left(\frac{T_{\text{before}}(q) - T_{\text{after}}(c, q)}{T_{\text{before}}(q)}\right) \times 100\%$$
3. **Oracle Best-Performing Candidate ($c^*(q)$):** The candidate within the eligible candidate pool $C_{\text{eligible}}(q)$ that achieves the maximum empirical runtime improvement on the live database:
   $$c^*(q) = \arg\max_{c \in C_{\text{eligible}}(q)} \Delta T_{\text{meas}}(c, q)$$

#### Methodological Requirements for Oracle Evaluation
- **Full Candidate Measurement Requirement:** Determining $c^*(q)$ requires physically deploying and benchmarking **every eligible candidate** $c \in C_{\text{eligible}}(q)$ for that evaluation query.
- **Strict Isolation of Oracle Telemetry:** To prevent candidate-level empirical measurements from leaking into Policy B or Policy C selection decisions, the evaluation MUST execute in **two strictly decoupled phases**:
  - **Phase 1 (Offline Policy Selection):** All policy selection decisions ($c_A, c_B, c_C$) for all test queries are computed against the **frozen TRAIN retrieval corpus** and locked in an immutable evaluation manifest before any physical candidate measurements occur.
  - **Phase 2 (Isolated Physical Measurement Stage):** In a separate evaluation stage, candidate-level physical benchmarks are conducted on PostgreSQL for each candidate, with complete index teardown and baseline verification between candidates.
  - *Scientifically Defensible Rationale:* Executing oracle measurement in a separate, decoupled stage (Option C) guarantees that no candidate-level runtime telemetry can influence Policy B or C selection, completely eliminating forward leakage.

## 5. Comparative A/B/C Execution Protocol on Identical Test Cases

To ensure a 100% fair and controlled comparison across Policies A, B, and C on every test query $q_{\text{test}} \in Q_{\text{test}}$:

```
                          ┌───────────────────────────┐
                          │ Unseen Test Query q_test  │
                          └─────────────┬─────────────┘
                                        │
                                        ▼
                  ┌───────────────────────────────────────────┐
                  │ Phase 1 Diagnostic & Candidate Generation │
                  │  Candidate Pool C = {c_1, ..., c_k}       │
                  │  HypoPG Simulation + Safety Eligibility   │
                  └─────────────────────┬─────────────────────┘
                                        │
             ┌──────────────────────────┼──────────────────────────┐
             ▼                          ▼                          ▼
   ┌───────────────────┐      ┌───────────────────┐      ┌───────────────────┐
   │ Policy A Decision │      │ Policy B Decision │      │ Policy C Decision │
   │ c_A = Baseline(C) │      │ c_B = Sim(C, TRAIN│      │ c_C = Out(C, TRAIN│
   └─────────┬─────────┘      └─────────┬─────────┘      └─────────┬─────────┘
             └──────────────────────────┼──────────────────────────┘
                                        │
                                        ▼ (Locked in Manifest)
                  ┌───────────────────────────────────────────┐
                  │ Sequential Physical Measurement on Live DB│
                  │                                           │
                  │ 1. Measure c_A -> Cleanup & Verify        │

                  └───────────────────────────────────────────┘
```

### 5.1 Step-by-Step Per-Case Execution Protocol
1. **Identical Query & Candidate Input:** Every test query $q_{\text{test}}$ produces a single, deterministic candidate pool $C(q_{\text{test}})$ through Phase 1 diagnosis and HypoPG counterfactual validation.
2. **Frozen Historical Retrieval Memory:** The historical memory index accessible to Policy B and Policy C is **strictly frozen to the TRAIN partition**. Test query definitions and test evaluation outcomes are never indexed in the retriever.
3. **Pre-Execution Policy Selection:** Policies A, B, and C evaluate $C(q_{\text{test}})$ offline and select candidates $c_A, c_B, c_C$.
4. **Physical Benchmark Execution:**
   - For each distinct candidate $c \in \{c_A, c_B, c_C\}$:
     - Baseline $T_{\text{before}}(q_{\text{test}})$ measured ($W=2, N=10$).
     - Physical index $c$ created via `CREATE INDEX CONCURRENTLY`.
     - Post-remediation $T_{\text{after}}(c, q_{\text{test}})$ measured ($W=2, N=10$).
     - Physical index $c$ dropped via `DROP INDEX IF EXISTS` + `DISCARD ALL`.
     - Pre-flight check asserts 0 `idx_autodba_*` indexes exist before testing the next candidate.
5. **Deduplication of Identical Policy Choices:** If Policy A, B, and C select the same candidate, that candidate is physically benchmarked exactly once, and its verified empirical measurement is assigned to all agreeing policies.
6. **Prevention of Test Outcome Leakage:** Outcomes measured during test evaluation are recorded solely in the experimental result log and are **never persisted into the live retrieval memory table** during the experiment.

### 5.2 Required Research Harness Capability
- `MeasuredCaseRunner.execute_pilot_case()` was designed specifically for single end-to-end measured case creation (including database memory insertion).
- **Required New Research Harness:** A research-only comparative evaluation harness (e.g. `research/comparative_runner.py` / extending `EvaluationHarness`) is required to orchestrate multi-policy candidate selection, deduplicated physical execution, automated inter-candidate teardown, and metric calculation without polluting the live `optimization_memories` table.

## 6. Experimental Contamination Controls & Limitations

| Potential Contamination Vector | Risk Description | Applied Control / Defense | Verification Mechanism |
| :--- | :--- | :--- | :--- |
| **Residual Physical Indexes** | Index from candidate $i$ remains active during candidate $i+1$, altering baseline plans. | `cleanup_index()` with `DROP INDEX IF EXISTS` under `AUTOCOMMIT`. | Runner pre-flight check asserts 0 `idx_autodba_*` indexes before every run. |
| **Plan Cache Bleed** | PostgreSQL backend caches parameterized query execution plans across runs. | `DISCARD ALL;` executed immediately following index drop. | Session reset clears prepared statements and cached plan trees. |
| **Cross-Partition Memory Retrieval** | Test query execution persists to `optimization_memories` and leaks into subsequent retrieval queries. | `EvaluationHarness` queries in-memory partitioned dataset, NOT live database table during evaluation. | Formal assertion `verify_split_leakage()` validates partition isolation. |
| **Workload Order Bias** | Sequential runs on the same table experience memory cache advantages. | Deterministic case execution with explicit plan cache purge between cases. | Standard deviation and CoV recorded on every run. |

### 6.1 Critical Experimental Limitations on Buffer Cache & Database Reset
- **Warmup Scope:** $W=2$ warmup runs mitigate immediate cold-start latency spikes, but they **do not reset or equalize PostgreSQL shared buffers**.
- **`DISCARD ALL` Scope:** `DISCARD ALL;` resets session-level cached plans, temporary tables, and prepared statements, but it does **not** flush shared buffer pages from RAM.
- **Persistent Cache Limitation:** Pages cached in PostgreSQL shared buffers by prior queries remain cached. This remains an inherent experimental characteristic of benchmark testing on a persistent database engine.

## 7. Real Runtime Benchmark Protocol ($W=2, N=10$)

### 7.1 Standard Measurement Specification
- **Warmup Repetitions ($W$):** Exactly 2 discarded runs per stage (mitigates cold-start plan compilation overhead).
- **Measured Repetitions ($N$):** Exactly 10 measured runs per stage.
- **Execution Order:**
  1. Pre-remediation baseline measurement (session-local `SET LOCAL enable_indexscan=off; SET LOCAL enable_bitmapscan=off`).
  2. Physical index creation via `CREATE INDEX CONCURRENTLY`.
  3. Post-remediation measurement (physical index enabled).
  4. Physical index drop via `DROP INDEX IF EXISTS` + `DISCARD ALL`.
- **Primary Metric:** Arithmetic mean execution time in milliseconds ($T_{\text{before}}, T_{\text{after}}$).
- **Secondary Metrics:** Median, min, max, standard deviation, coefficient of variation ($\text{CoV} = \frac{\sigma}{\mu}$), shared buffer hit blocks, shared buffer read blocks, rows removed by filter.

### 7.2 Noise and Invalidation Thresholds
- **High Variance Threshold:** If baseline $\text{CoV} > 0.50$, the measurement is flagged as noisy.
- **Execution Anomaly:** If $T_{\text{before}} \le 0.001\text{ ms}$ or if rows returned do not match expected cardinality, the run is flagged as invalid and excluded.

## 8. Experimental Evaluation Metrics

### 8.1 Primary Metrics

| Metric | Formal Definition | Desired Direction |
| :--- | :--- | :--- |
| **Mean Post-Remediation Runtime** | $\bar{T}_{\text{after}} = \frac{1}{|Q_{\text{test}}|} \sum_{q \in Q_{\text{test}}} T_{\text{after}}(q, \text{Policy}(q))$ | Lower is better |
| **Mean Runtime Improvement ($\Delta T\%$)** | $\Delta T\% = \frac{1}{|Q_{\text{test}}|} \sum_{q \in Q_{\text{test}}} \left(\frac{T_{\text{before}}(q) - T_{\text{after}}(q, \text{Policy}(q))}{T_{\text{before}}(q)}\right) \times 100\%$ | Higher is better |
| **Regression Rate ($R_{\text{reg}}\%$)** | $\frac{|\{q \in Q_{\text{test}} \mid T_{\text{after}}(q) > T_{\text{before}}(q)\}|}{|Q_{\text{test}}|} \times 100\%$ | Lower is better ($0\%$ ideal) |
| **Top-1 Selection Agreement** | Agreement rate between Policy B/C selection and Oracle candidate $c^*(q)$. | Higher is better |
| **Safety Violation Rate** | Rate of selecting an unvalidated or safety-rejected candidate. | **Strictly 0.0%** (Hard constraint) |

### 8.2 Secondary Metrics
- **Planner Cost Improvement ($\Delta_{\text{cost}}\%$):** Percentage drop in estimated total cost.
- **Fallback Frequency ($F_{\text{fallback}}\%$):** Rate at which Policy B or C falls back to Policy A due to absence of matching historical cases.
- **Selection Overhead ($t_{\text{select}}\text{ ms}$):** Time required to compute similarity and outcome rankings (target $< 5\text{ ms}$).
- **Historical Support Count:** Average number of matching historical cases per candidate.

## 9. Hyperparameter Strategy & Tuning Protocol

### 9.1 Hyperparameter Definitions
- **$\alpha$ (Similarity Weight in Policy B):** Default `1.0`. Controls similarity boost to HypoPG cost score.
- **$\beta$ (Outcome Weight in Policy C):** Default `1.0`. Controls empirical outcome boost to HypoPG cost score.
- **$\lambda_{\text{reg}}$ (Asymmetric Regression Penalty in Policy C):** Default `1.5` (test range `1.0` to `3.0`). Multiplier penalizing historical candidates that caused measured regressions.

### 9.2 Strict Tuning Boundary
- **Zero Test Contamination Rule:** Hyperparameters $\alpha, \beta, \lambda_{\text{reg}}$ must **NEVER** be tuned or selected using the held-out TEST partition.
- **Tuning Method:** Leave-one-template-out cross-validation (LOOCV) **exclusively within the TRAIN partition**.
- If TRAIN has $K$ templates, evaluate cross-validation performance by holding out 1 Train template at a time, selecting $\alpha, \beta, \lambda_{\text{reg}}$ that maximize mean $\Delta T\%$ on the held-out Train templates.

## 11. Audit Classification & Readiness Summary

### CONFIRMED (Established by Repository & Pilot)
1. `MeasuredCaseRunner` successfully executes end-to-end closed-loop optimization on PostgreSQL 17.11 with zero logic duplication.
2. Verified measured memory ID `1` exists with `provenance = MEASURED`, `is_verified = True`, `verification_state = VERIFIED_MEASURED`.
3. Ownership-aware cleanup reliably drops transient physical indexes (`idx_autodba_*`) and discards plan caches.
4. `CandidateSelector` implements Policy A, B, and C with exact canonical candidate key matching and asymmetric regression penalties.
5. `grouped_template_split` formally guarantees zero template and instance overlap between Train and Test.

### DESIGN DECISIONS (Established for Phase 6)
1. Corpus size established as **12 cases / 6 templates (minimum defensible target)** and **20 cases / 8 templates (desired target)**, with final size dictated by valid qualified cases.
2. Benchmark protocol locked to **$W=2$ warmup runs, $N=10$ measured repetitions**.
3. Hyperparameter tuning locked strictly to **LOOCV within the TRAIN partition** ($\lambda_{\text{reg}} \ge 1.0$).
4. Policy comparison protocol decoupled into **offline frozen-TRAIN selection** followed by **sequential physical measurement** with automated inter-candidate teardown.
5. Oracle candidate defined as $\arg\max_{c \in C_{\text{eligible}}} \Delta T_{\text{meas}}(c)$, evaluated in a separate isolated stage without leaking candidate timings into policy inputs.

### OPEN RISKS & METHODOLOGICAL BOUNDARIES
1. **Synthetic Data Scale:** The test database contains 5,000 orders and 15,000 order items. While sufficient for measurable index scan vs sequential scan plan transitions, real-world multi-gigabyte production workloads will exhibit different I/O latency profiles.
2. **Buffer Pool Warmth & Cache Reset:** $W=2$ warmups mitigate cold-start spikes but do not equalize shared buffers; `DISCARD ALL` resets plan caches but does not flush buffer pool RAM. This remains an inherent experimental limitation.
3. **Statistical Power:** Small corpus sizes ($M=12\text{--}20$) allow rigorous algorithmic validation on real database engines, but cannot claim broad generalizability across all arbitrary SQL workloads.
